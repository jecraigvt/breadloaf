# Breadloaf Hill plan for a 15 GB family archive

November 18, 2026

See [Import and recover family scan folders](archive-folder-import.md) for setup, permissions, and the recovery drill.

Use the scans the family already has. The site should accept a folder of scans in one import, preserve the original files, and let Bucky answer questions with links to the documents and pages it read. Size the system to hold at least 15 GiB of originals, about 16.1 GB, plus room for the catalog, new scans, and recovery copies.

**For a collection under 10 GB, use the free property Google Drive.** Use a dedicated, private scan archive folder in `breadloafhillsite@gmail.com`. The November 18 quota check showed about **14.1 GB free out of 15 GB** when both are expressed in Google's quota units. Confirm the actual scan size and remaining space before import. Allow for Gmail, Photos, and ongoing weekly backups in the same quota. [Google storage quota](https://support.google.com/googleone/answer/9004014?hl=en)

**At 10 GB or above, review the measured size and available space before choosing storage.** At the 15 GiB design target the originals would exceed the property account's currently available quota. To keep a collection of that size on the property Drive, Google One Basic is advertised at **$1.99 per month in the US for 100 GB total**. [Google One plans](https://one.google.com/about/plans?hl=en_US)

**Lower cost online option.** If the originals need more space than the free property Drive can spare, use a private **Cloudflare R2 Standard** bucket and keep the site's small encrypted backups in the shared Drive folder. Storing one 15 GB copy all month costs about **$0.08 per month for storage** with the 10 GB-month allowance available. Requests above the included usage, a second copy, and AI processing are separate costs. The site still needs an importer and can serve the files through its existing signed-in archive. [R2 pricing](https://developers.cloudflare.com/r2/pricing/)

## Import and read a whole collection

The current uploader accepts up to 100 MB per file. The background uploader accepts up to 20 files and 100 MB total per batch, and the current Bucky reader loads each source into memory. The new importer should handle individual originals larger than 512 MB without increasing the website's memory requirement in proportion to the file size. [Current upload limit](../src/lib/upload.ts), [Current background reader](../src/lib/bucky-job-handlers.ts)

1. **Inventory the source folder.** Show total bytes, number of files, formats, and expected pages before transfer. Keep relative folder paths, original filenames, and page order. Let the uploader group image files that are pages of one letter or record. Show which files can be read immediately and which need an additional reader, such as some TIFF scans. Accept intact originals separately from analysis eligibility.
2. **Upload once and resume after a disconnect.** A signed-in curator opens **Archive → Import folder**, selects a folder on their computer, and sees progress on the site. Breadloaf's existing sign-in controls who can start an import. The property account authorizes the site's Drive connection once, so uploaders can use the importer with their Breadloaf login alone. The server keeps the cloud credentials and opens an upload session for each approved file in the dedicated folder. Record progress per file in PostgreSQL and send bytes to storage in chunks using resumable Drive transfers or multipart R2 uploads. Pilot the browser transfer, with a desktop folder importer using the same batch records if needed. For Drive, create the destination and files through the app with its per-file scope. Files placed in Drive by hand require explicit authorization before the app can read them. [Drive resumable uploads](https://developers.google.com/workspace/drive/api/guides/manage-uploads#resumable), [Drive file scope](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [R2 uploads](https://developers.cloudflare.com/r2/objects/upload-objects/)
3. **Verify and catalog each original.** Check byte count and compute SHA-256 incrementally before marking a file saved. Limit concurrent transfers and use fixed-size chunks, for example 8 MiB, so each transfer uses bounded memory. Reuse the verified file on retry and keep separate catalog entries for distinct records that happen to have identical bytes. Use 64-bit byte counts and store a storage reference in the document catalog. Keep original downloads and previews behind the current site access checks. Existing documents can keep their current storage locations. [Current document schema](../prisma/schema.prisma), [Existing access checks](../src/app/api/documents/%5Bid%5D/file/route.ts)
4. **Read the batch in the background.** Queue each original as soon as its upload and checksum check succeed. Bucky can start reading the first files while the rest of the folder uploads. For large PDFs, have the worker stream the original to temporary disk and render a few pages at a time within its memory and disk limits. Extract an existing text layer when present and use OCR or vision for scanned pages. Store page text, a separate summary, the original page reference, and any legible document dates and names. Flag unreadable pages and uncertain handwriting for review. Show reading progress separately from upload progress. Checkpoint completed pages so a retry can read the original from Drive without a fresh upload. Measure pages per hour and any paid cost on a pilot. Keep the existing worker quota reserve and paid budget in effect. [Bucky background work](bucky-hybrid-implementation.md)
5. **Find and open the original from Bucky.** A request like “Show me the letter from 1972” searches document dates and indexed page text. Bucky presents matching letters and links to the relevant pages when known. When a family member opens a result, Breadloaf checks their access and streams the scan from private storage into the archive viewer. Readers use their Breadloaf sign-in. [Existing access checks](../src/app/api/documents/%5Bid%5D/file/route.ts)

## Preserve and recover the collection

The existing job packages the database and local uploads as a single encrypted ZIP. Creation streams the data, but verification reads the encrypted file and decrypts the ZIP into memory before checking the contents. The **512 MB** cap bounds that work on the website host. The upload to Drive is already resumable. Increasing the cap would leave the verification and restore memory problem in place. [Snapshot verification](../scripts/archive-common.ts#L110), [Archive recovery](archive-recovery.md)

Copy newly added or changed originals to an independent destination and verify their checksums. Preserve the previous recovery version if a source file is replaced or deleted. Keep a streaming encrypted backup of the database and a portable catalog that maps folder paths and documents to verified originals. Verify each catalog backup against the same set of original versions. Keep the present weekly backup running until the replacement passes a restore.

Keep an encrypted copy outside the primary account and storage service. With Drive as primary, a separately controlled R2 bucket is one option. An off-site drive owned by the family works with either primary storage choice. Give a family custodian access to the recovery key outside the property account and document how to export and restore the collection.

## Test and rollout

1. Pilot typed letters, difficult handwriting, a large scanned PDF, and any uncommon image formats in the collection. Ask Bucky to find a letter by year and verify that the result opens the original for a signed-in family member. Check exact downloads, page links, and the list of pages needing review. Use the sample to estimate reading time and cost.
2. Test an import of at least 15 GiB with representative file counts, including a single scanned PDF over 512 MB. Measure peak website memory during upload and peak worker memory during reading. Interrupt that file's transfer and a Bucky job, then verify both can resume without losing or duplicating originals. Verify that a regular family reader can open an allowed file and that an unsigned visitor cannot.
3. Restore the catalog and originals into an isolated environment with the property account unavailable. Compare file counts and checksums, open original scans, and run sample searches. Confirm that a missing backup, a failed copy, or low quota is visible to the caretaker. Repeat the recovery drill periodically. Begin the full family import once the chosen storage has capacity and the recovery drill passes.
