## Import and read a whole collection

The current uploader accepts up to 100 MB per file. The background uploader accepts up to 20 files and 100 MB total per batch, and the current Bucky reader loads each source into memory. The new importer should handle individual originals larger than 512 MB without increasing the website's memory requirement in proportion to the file size. [Current upload limit](../src/lib/upload.ts), [Current background reader](../src/lib/bucky-job-handlers.ts)

1. **Inventory the source folder.** Show total bytes, number of files, formats, and expected pages before transfer. Keep relative folder paths, original filenames, and page order. Let the uploader group image files that are pages of one letter or record. Show which files can be read immediately and which need an additional reader, such as some TIFF scans. Accept intact originals separately from analysis eligibility.
2. **Upload once and resume after a disconnect.** A signed-in family member opens **Archive → Import folder**, selects a folder on their computer, and sees progress on the site. Breadloaf's existing sign-in controls who can start an import. The property account authorizes the site's Drive connection once, so uploaders can use the importer with their Breadloaf login alone. The server keeps the cloud credentials and opens an upload session for each approved file in the dedicated folder. Record progress per file in PostgreSQL and send bytes to storage in chunks using resumable Drive transfers or multipart R2 uploads. Pilot the browser transfer, with a desktop folder importer using the same batch records if needed. For Drive, create the destination and files through the app with its per-file scope. Files placed in Drive by hand require explicit authorization before the app can read them. [Drive resumable uploads](https://developers.google.com/workspace/drive/api/guides/manage-uploads#resumable), [Drive file scope](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [R2 uploads](https://developers.cloudflare.com/r2/objects/upload-objects/)
3. **Verify and catalog each original.** Check byte count and compute SHA-256 incrementally before marking a file saved. Limit concurrent transfers and use fixed-size chunks, for example 8 MiB, so each transfer uses bounded memory. Reuse the verified file on retry and keep separate catalog entries for distinct records that happen to have identical bytes. Use 64-bit byte counts and store a storage reference in the document catalog. Keep original downloads and previews behind the current site access checks. Existing documents can keep their current storage locations. [Current document schema](../prisma/schema.prisma), [Existing access checks](../src/app/api/documents/%5Bid%5D/file/route.ts)
4. **Read the batch in the background.** Queue each original as soon as its upload and checksum check succeed. Bucky can start reading the first files while the rest of the folder uploads. For large PDFs, have the worker stream the original to temporary disk and render a few pages at a time within its memory and disk limits. Extract an existing text layer when present and use OCR or vision for scanned pages. Store page text, a separate summary, the original page reference, and any legible document dates and names. Flag unreadable pages and uncertain handwriting for review. Show reading progress separately from upload progress. Checkpoint completed pages so a retry can read the original from Drive without a fresh upload. Measure pages per hour and any paid cost on a pilot. Keep the existing worker quota reserve and paid budget in effect. [Bucky background work](bucky-hybrid-implementation.md)
5. **Find and open the original from Bucky.** A request like “Show me the letter from 1972” searches document dates and indexed page text. Bucky presents matching letters and links to the relevant pages when known. When a family member opens a result, Breadloaf checks their access and streams the scan from private storage into the archive viewer. Readers use their Breadloaf sign-in. [Existing access checks](../src/app/api/documents/%5Bid%5D/file/route.ts)

## Preserve and recover the collection

The updated weekly backup streams the database and local uploads during creation, verification, and restore. It uses private temporary disk to authenticate the archive and check each file's checksum. It can still read backups written by the previous version. [Archive recovery](archive-recovery.md)

Keep the weekly backup for the database and local uploads. The Drive scan originals live in the shared Scan Archive folder. Viewer access opens those same originals and ends if the owner permanently deletes them. [Google Drive deletion and shared access](https://support.google.com/drive/answer/2375102?hl=en)

If the family later chooses to keep a separate recovery copy, the collection command can save an encrypted database backup, a portable catalog, and verified originals to independently controlled storage. [Optional recovery setup](archive-folder-import.md#optional-independent-recovery-copy)

## Test and rollout

1. Pilot typed letters, difficult handwriting, a large scanned PDF, and any uncommon image formats in the collection. Ask Bucky to find a letter by year and verify that the result opens the original for a signed-in family member. Check exact downloads, page links, and the list of pages needing review. Use the sample to estimate reading time and cost.
2. Test an import of at least 15 GiB with representative file counts, including a single scanned PDF over 512 MB. Measure peak website memory during upload and peak worker memory during reading. Interrupt that file's transfer and a Bucky job, then verify both can resume without losing or duplicating originals. Verify that a regular family reader can open an allowed file and that an unsigned visitor cannot.
3. Verify Jeremy can open the pilot scans from his personal Google account. Begin the full family import once the pilot passes and the property Drive has space for the measured collection.
